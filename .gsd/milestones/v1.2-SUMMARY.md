## Lessons Learned
- **Schema Guards at Boundaries**: `getValidatedJSON` with Zod + auto-eviction prevented a class of silent corruption bugs when persisted data shapes evolve across app versions.
- **Dispatcher-Side Seen Pairs**: Keeping "seen" state in Redis (not per-engine) was the correct call; it enables multi-device fairness and makes the engine itself fully portable/reconstructable from events.
- **Cooldown vs Lock**: Pair locks (short TTL) and user cooldowns (longer TTL) solve different problems; conflating them leads to either starvation or collision — keeping them separate paid off.
- **Scale-to-Zero + BullMQ**: Fly.io scale-to-zero requires BullMQ worker process separation; co-locating worker and API in one process caused queue stalls on cold boot.

## Core Library Gap Finding (at close of v1.2)
A post-milestone audit against the original product implementation plan revealed that `@taste-engine/core` itself has 7 structural gaps not addressed during v1.2 (which was focused on product layers above the library). These are the target of **v1.3 — Core Hardening**:
1. Shared RNG between `status()` and `nextPair()` breaks determinism.
2. `seedSchedule()` mutates `pairCounts` as a side effect.
3. `addItems()` onboarding can return fewer pairs than `anchorsPerNewItem` (failing test).
4. `loadSnapshot()` replays events instead of restoring stored item states.
5. Cycle guard is detection-only; `alarmThreshold` is unused; no response behavior.
6. `minUniqueOpponentsInPool`, `strength`, `userId`, `context` are declared but not wired.
7. Benchmark tests block `npm test`; no coverage script; `nextPair()` sorts all items (not just pool).
