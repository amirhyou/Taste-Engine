# Plan 9.2: Moderation + Abuse Guardrails

## Objective
Introduce admin/moderation controls with strict server-side authorization, and add API guardrails (rate limiting + request size caps) for public discovery traffic.

## Context
- `.gsd/phases/9/RESEARCH.md` — OWASP guidance, rate limiting options
- `examples/social-server/src/api/routes.ts` — current route definitions
- `examples/social-server/src/redis/client.ts` — Redis access
- `examples/social-server/src/redis/cooldown.ts` — existing user cooldown logic
- `examples/social-server/src/dispatch/RedisDispatcher.ts` — vote/next guardrails

## Tasks

<task type="auto">
  <name>Add shared rate limit + size guard middleware</name>
  <files>
    examples/social-server/src/api/middleware/rateLimit.ts
    examples/social-server/src/api/middleware/bodyLimit.ts
    examples/social-server/src/api/routes.ts
  </files>
  <action>
    Implement two middleware helpers and apply them to high-risk routes.

    `rateLimit.ts`:
    - Fixed-window limiter using Redis (key: `rl:{scope}:{id}`)
    - Expose `rateLimit({ scope, limit, windowSec, keyFromRequest })`
    - On limit exceeded, return 429 with `Retry-After` and `RateLimit-*` headers
    - Use Redis `INCR` + `EXPIRE` on first hit in window

    `bodyLimit.ts`:
    - Enforce a max JSON body size per route (default 50kb)
    - Reject with 413 if exceeded

    Apply in `routes.ts`:
    - `POST /contests` (create): rate limit + body size
    - `POST /contests/:id/vote`: rate limit + body size
    - `GET /contests/:id/next`: rate limit
    - `GET /discover`: rate limit

    Keying:
    - Use `x-forwarded-for` or `c.req.header('x-real-ip')` when available; fallback to `c.req.raw.headers.get('x-forwarded-for')` or `c.req.raw.headers.get('cf-connecting-ip')`
    - If no IP, fall back to `userId` for vote/next routes
  </action>
  <verify>rg -n "rateLimit\(|bodyLimit|Retry-After|RateLimit-" examples/social-server/src/api</verify>
  <done>
    - Rate limit middleware exists and returns 429 with standard headers
    - Body size guard returns 413 on oversized JSON payloads
    - All specified routes are protected
  </done>
</task>

<task type="auto">
  <name>Add admin auth + moderation endpoints</name>
  <files>
    examples/social-server/src/api/admin.ts
    examples/social-server/src/api/routes.ts
    examples/social-server/src/redis/moderation.ts
  </files>
  <action>
    Add a small admin sub-router with JWT auth and explicit role checks.

    `admin.ts`:
    - Use Hono JWT middleware (`import { jwt } from 'hono/jwt'`)
    - Require `AUTH_JWT_SECRET` env var
    - Verify token has `role: 'admin'`
    - Expose admin routes:
      - `POST /admin/contests/:id/hide` -> `hideContest(id)`
      - `POST /admin/contests/:id/lock` -> `lockContest(id)`
      - `POST /admin/devices/ban` -> `banDevice(deviceId)`

    `moderation.ts`:
    - Redis helpers for device bans
      - Key: `ban:device:{deviceId}` with optional TTL
      - `banDevice(deviceId, ttlSec?)`
      - `isDeviceBanned(deviceId)`

    In `routes.ts`:
    - Mount `admin` sub-router (e.g. `app.route('/', adminApp)`)
    - For public routes, check `isDeviceBanned` when `x-device-id` header is present
      - If banned, return 403

    Notes:
    - Keep error responses JSON `{ error: message }`
    - Do not expose admin routes without JWT enforcement
  </action>
  <verify>rg -n "admin|jwt|AUTH_JWT_SECRET|ban:device" examples/social-server/src/api examples/social-server/src/redis</verify>
  <done>
    - Admin routes are protected by JWT and role checks
    - Banned devices are blocked on public endpoints
  </done>
</task>
