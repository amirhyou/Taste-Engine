# Plan 9.1: Publish + Discovery Surface

## Objective
Add a publishable contest metadata layer with invite links and a public discovery listing, then wire it into the existing Hono API so contests can transition from private to immutable/public.

## Context
- `.gsd/phases/9/RESEARCH.md` — rate limiting + admin auth guidance
- `.gsd/ARCHITECTURE.md` — repo structure
- `examples/social-server/src/api/routes.ts` — current Hono routes
- `examples/social-server/src/coordinator/ContestCoordinator.ts` — contest lifecycle
- `examples/social-server/src/dispatch/RedisDispatcher.ts` — vote/next routing
- `examples/social-server/src/redis/client.ts` — shared Redis client

## Tasks

<task type="auto">
  <name>Add contest metadata + invite storage in Redis</name>
  <files>
    examples/social-server/src/redis/contestMeta.ts
  </files>
  <action>
    Create `src/redis/contestMeta.ts` that manages contest metadata and discovery indices.

    Data model (Redis):
    - Hash: `contest:meta:{id}`
      Fields: `id`, `status`, `createdAt`, `publishedAt`, `inviteCode`, `title`, `description`
    - String: `contest:invite:{code}` -> contestId
    - ZSET: `contest:published` score=publishedAt, value=contestId

    Functions to export:
    - `createContestMeta({ id, title?, description? }): Promise<{ inviteCode: string }>`
      - Generates `inviteCode` (base64url from `crypto.randomBytes`) and stores hash + invite mapping
      - Sets `status` = `draft`, `createdAt` = Date.now()
    - `getContestMeta(id): Promise<ContestMeta | null>`
    - `publishContest(id): Promise<void>`
      - Sets `status` = `published`, `publishedAt` = Date.now()
      - Adds `id` to `contest:published` ZSET
    - `hideContest(id): Promise<void>`
      - Sets `status` = `hidden` and removes from published ZSET
    - `lockContest(id): Promise<void>`
      - Sets `status` = `locked` (immutable, not public)
    - `resolveInvite(code): Promise<string | null>`

    Rules:
    - Use Redis client from `./client`
    - Keep all dates in epoch ms
    - If `publishContest` is called twice, do not create duplicate ZSET entries
  </action>
  <verify>rg -n "contest:meta|contest:invite|contest:published" examples/social-server/src/redis/contestMeta.ts</verify>
  <done>
    - `contestMeta.ts` exports the functions above
    - Invite lookup and publish list can be derived from Redis data only
  </done>
</task>

<task type="auto">
  <name>Wire publish, invite, and discovery endpoints</name>
  <files>
    examples/social-server/src/api/routes.ts
    examples/social-server/src/dispatch/RedisDispatcher.ts
  </files>
  <action>
    Update routes and dispatcher to support publish + discovery flows.

    In `routes.ts`:
    - Extend `POST /contests` to accept optional `title` and `description`
      - Call `createContestMeta(...)` and return `{ contestId, inviteCode }`
    - Add `POST /contests/:id/publish`
      - Marks contest as published via `publishContest`
      - Returns `{ status: 'published' }`
    - Add `GET /contests/:id` to return contest metadata
    - Add `GET /discover?limit=&offset=` (or `cursor`) to list published contests
      - Use `contest:published` ZSET ordering (newest first)
      - Return `items: ContestMeta[]`
    - Add `GET /invites/:code` to resolve invite -> contest metadata

    In `RedisDispatcher`:
    - Check contest status before `getNextPair` and `submitVote`
      - If status is `locked` or `published`, throw `HttpError(409, 'Contest locked')`
      - If status is `hidden`, return `HttpError(404, 'Contest not found')`
    - Use `getContestMeta` for the status check

    Notes:
    - Keep existing error-handling style (`HttpError`)
    - Do not change pair/seen/lock logic
  </action>
  <verify>rg -n "publish|discover|invites|Contest locked" examples/social-server/src/api/routes.ts examples/social-server/src/dispatch/RedisDispatcher.ts</verify>
  <done>
    - API returns invite codes and supports publish/discover/invite lookups
    - Dispatcher blocks voting on locked/published contests
  </done>
</task>
